# 我的内容规划

个人内容计划表，使用 React、TypeScript、Vite、Supabase Auth 和 PostgreSQL。页面可运行在 Mac 或 GitHub Pages；正式数据通过本人登录保存在同一个 Supabase 项目。

本仓库只包含通用应用代码、数据库迁移和独立验收数据。私人规划、资料正文、备份、环境文件不属于公开仓库。

## 本机运行

需要 Node.js 24 或更新的兼容版本。复制 `.env.example` 为 `.env`，填写同一个项目的 URL、publishable key、project ID。这些是浏览器公开配置；数据库密码、OAuth Client Secret、service role key 只能留在服务后台。

```sh
npm ci
npm run check
```

Mac 双击 `启动网站.command`，浏览器打开 `http://127.0.0.1:18765/`。双击 `停止网站.command` 停止对应服务。运行脚本绑定本机回环地址，进程独立于终端；关闭 Codex 不会由脚本主动停止服务。数据保存仍需要联网。

重复启动会复用已核对身份的本应用。端口被占用时提示并停止启动；停止脚本核对 PID、命令路径和健康标记后才结束进程，不会主动关闭同端口其他服务。可运行 `node scripts/local.mjs status` 检查状态，日志在忽略的 `.runtime/server.log`。

开发使用 `npm run dev`。独立页面验收使用 `npm run qa`，地址 `http://127.0.0.1:18766/`。验收模式用临时 PostgreSQL 引擎和通用测试事项，刷新会重建；不能用它保存个人计划，也不能证明 Supabase 登录已经通过。Vite 拒绝构建验收模式，正式构建不包含验收适配器。

## 日常使用

1. 新建方向；网站附带一个“零散选题”计划，也可以继续建立具体计划。
2. 新建事项只需标题。可以补充平台、批次、分组、目标、大纲、完成标准和计划日期。
3. 开始时切换“进行中”，完成时勾选。实际开始和完成时间支持修正；只记得日期时选择日期精度。
4. 历时包含等待与休息。实际投入按分钟手动登记，可修正或撤销；两者分别显示。
5. 详情文字通过“保存事项”提交。完成勾选单独保存状态和时间，未保存文字保留为本地草稿。
6. “资料与规则”管理计划自己的引用与版本；“归档计划”管理名称、目标、默认完成标准和复查周期。新计划默认不开复查周期。
7. 移入回收站可恢复；误勾撤销恢复原状态；返工重开保留原开始时间。批次结项保存当时记录，后续改动不会重写它。

进度按完整业务范围统计，状态和搜索筛选只改变显示行。取消事项退出有效分母，已有投入另列。首次范围、新增与移出分别显示；首次导入可携带原定范围快照。

保存响应丢失时显示“结果待确认”。核对原发生时间后重试会使用原请求号，数据库返回原结果；不要通过新增另一条记录代替。冲突或恢复后的旧页面会拒绝覆盖，请刷新并核对草稿。显式退出清除本入口私人草稿；会话失效保留供本人重登核对。

## 数据与恢复

在“备份与设置”下载完整 JSON；确认文件已落盘并独立保管。7 天提醒只是站内提示，最近触发下载不等于已核验磁盘备份。JSON 包含业务记录、投入、历史、资料与结项，不包含会话、账号配置和素材文件。网页链接与本地路径只保存引用。

导入先验证 SHA-256、结构、数量和关联，再预览。合并仅增加新 UUID，同编号保留当前数据。完整恢复将业务集合恢复至备份时点，备份后新增记录退出当前集合；操作前快照可找回之前状态。完整恢复后生成新数据代次，旧请求不能继续写入。

应用快照与正式数据位于同一服务，不是独立备份。最多保留 30 份且总负载预算 50 MiB；重要范围操作必须成功保存前置快照。备份单次 JSON 上限 16 MiB，超出时明确拒绝；此上限不代表所有规模都做过性能验收。

## Supabase 初始化

在空项目按文件名顺序执行 `supabase/migrations/` 中全部迁移：001、002、003，以及 `20261015140245_scope_singleton_updates.sql`。最后一份为控制行更新增加明确的本人和单例条件，兼容云端更新保护。迁移需要管理员入口；应用客户端不能执行管理操作。

启用 GitHub OAuth。OAuth 应用的 callback 使用该 Supabase 项目的 `/auth/v1/callback`；Supabase Site URL 为正式 Pages 地址，Redirect URLs 精确加入本机地址及 Pages 子目录地址。OAuth Client Secret 只填写到 Supabase 后台。

首次绑定前所有客户端拒绝访问。网站完成 GitHub 登录后，管理员核对 `auth.identities` 中 provider 为 github 且 provider_id 对应预先确认的不可变 GitHub 数字 ID，再将 `planner_control.owner_id` 绑定该用户 UUID。不能使用首访者自动注册为 owner，也不能信任可编辑的用户名或 user_metadata。绑定后关闭新用户注册并验证已有本人仍能登录。

四张业务／辅助表均启用 RLS。客户端只有受控读取与指定函数执行权限；写入经过固定 owner 校验、修订检查、事务、操作去重和恢复代次检查。控制表和去重台账没有客户端查询策略，这是有意的默认拒绝。安全检查中 authenticated 可执行的受控 definer 函数需要结合函数体 owner 检查核对。

## GitHub Pages

仓库目录必须为本应用目录，不能把上级私人工作目录初始化进仓库。仓库 Actions Variables 配置三个 `VITE_SUPABASE_*` 公开变量；Pages Source 选择 GitHub Actions。

自动部署已在 `.github/workflows/pages.yml` 启用；推送 main 后执行检查与发布。若命令行凭据没有 workflow 权限，工作流文件可通过已有 GitHub 网页登录维护，无需扩大命令行授权。工作流执行锁定依赖安装、测试、正式构建、公开文件扫描和 Pages 部署。项目站点 base 为 `/personal-content-planner/`，路由使用 hash，刷新无需服务器改写。改变仓库名时同步 base、OAuth homepage 和 Supabase 回跳白名单。

发布前运行 `npm run check` 并检查暂存文件、仓库历史、产物、Actions 日志与附件。扫描器是辅助检查，不能代替人工核对公开范围。发布后匿名检查实际站点和静态资源，登录前不得显示私人内容。

## 换项目重建

在替代空项目执行迁移，重新配置 OAuth、本人绑定和关闭注册，核对项目 ID，再通过页面预览恢复独立 JSON。更新本机环境和 Pages 变量，分别登录读取同一记录后才切换正式入口。前端回退不等于数据库回退；迁移前先保存独立备份并在隔离实例演练。

完整账号登录、另一真实身份、跨入口读写与空替代项目重建需要对应认证环境。局部数据库测试不能替代这些验收，应在私有交付记录中逐项登记实际结果。
